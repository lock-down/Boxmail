# 开发、联调与版本维护

`0.0.1` 是 Boxmail 的本地初始基线，包含原生客户端、本机后端、测试和设计导出。后续修复从该基线继续提交，保留可追踪的变更记录。

## 修改与验证

从仓库根目录执行命令。客户端布局和操作主要位于 `Sources/Boxmail/Views/`，状态与接口调用位于 `Stores/MailStore.swift`；邮件协议和 AI 行为分别位于 `Backend/src/mail.js` 与 `agent.js`。

修改接口时，一并检查 `Sources/BoxmailCore/Models.swift`、后端路由和调用方，并用测试覆盖实际的数据契约或行为变化。新增邮件发送、同步或 AI 动作时，保留发送确认、结果不确定时禁止重发、分类确认及撤销等行为。

```bash
git switch -c fix/mail-sync
./script/test.sh
./script/build_and_run.sh --verify
git diff --check
git status --short
```

分支名按实际改动调整。`test.sh` 包含后端和 Swift 测试，并处理当前 Command Line Tools 的测试宏加载问题。`--verify` 只确认构建和启动，不等同于界面或服务验证；修改了界面、发送或同步行为，需要检查对应流程。调试启动可使用 `./script/build_and_run.sh --debug`。

提交前审阅 `git diff` 和暂存区，按一个可说明的问题提交，注明修改原因、验证结果及仍待确认的项目。不要提交邮箱授权码、API Key、真实邮件缓存、附件、数据库或构建产物。

## 联调检查

使用专门的测试邮箱、测试收件人和单独的后端数据目录。记录邮箱服务商、服务器参数、模型、操作步骤、预期及实际结果，错误日志去除凭证和邮件隐私内容。

| 流程 | 检查内容 |
| --- | --- |
| 账户 | 添加、测试连接、保存、重新启动、移除账户 |
| 同步 | 文件夹识别、再次同步、已读与星标、移动、网络失败后的恢复 |
| 写信 | 草稿自动保存、重启恢复、附件、回复与转发、发送确认、重复点击 |
| AI | 连接测试、摘要、待办、回复草稿、分类确认与撤销、失败提示 |
| 附件 | 文本提取、中文搜索、预览、保存及不支持格式的提示 |
| 生命周期 | 关闭和重启 App、中断任务、后端进程退出、本机数据保留 |

发送结果显示不确定时，先在服务商已发送文件夹和测试收件人邮箱确认实际投递，再决定后续处理。自动化测试通过后仍需验证真实服务商行为，当前 0.0.1 尚未完成这部分联调。

## 版本更新

版本采用 `主版本.次版本.修订版本`。当前阶段，联调修复依次发布 `0.0.2`、`0.0.3`；集中新增功能可进入 `0.1.0`。每个版本都更新变更记录并建立对应 Git 标签。

以更新到 `0.0.2` 为例：

1. 把根目录 `VERSION` 改为 `0.0.2`，构建脚本会据此生成 App 版本，设置页读取 App 元数据。
2. 更新后端包版本和锁文件：

   ```bash
   npm version 0.0.2 --prefix Backend --no-git-tag-version
   ```

3. 在 `CHANGELOG.md` 增加版本日期、用户可见变化和验证范围，检查 README 中当前版本及功能限制是否需要调整。
4. 完成适用的测试、构建和联调，将本次修改提交后再建立版本标签：

   ```bash
   git add VERSION Backend/package.json Backend/package-lock.json CHANGELOG.md
   git diff --cached --check
   git commit -m "chore: release v0.0.2"
   git tag -a v0.0.2 -m "Boxmail v0.0.2"
   git status --short
   ```

功能源码和文档修改也需要审阅并纳入提交，以上暂存命令只列出了版本元数据。数据库 `user_version` 独立于 App 版本，修改数据结构前先设计迁移、备份和旧数据兼容验证。

已建立的版本标签保持不动，后续修复创建新版本。当前仅维护本地仓库；配置远程和推送由后续协作需要决定。
