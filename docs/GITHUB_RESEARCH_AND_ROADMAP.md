## 2. Boxmail v0.0.5 调研基线与缺口

现有基础包括多账户 IMAP/SMTP 收发、定时轮询、HTML 和 CID 阅读、本机草稿、附件搜索、单封邮件 AI、可恢复的后台整理，以及分类确认和撤销。发送也已区分成功、进行中和结果不确定，禁止对结果不确定的发送自动重试。这些能力应在后续迁移中保留。

| 观察 | 已核实的实现 | 对每日使用的影响 |
| --- | --- | --- |
| 历史同步范围有限 | `Backend/src/mail.js:182` 从文件夹末尾取最近 200 封；没有历史分页回填 | 早期邮件可能从未进入本机缓存，现有本机搜索无法找到它们 |
| 刷新按全量快照传输 | `Backend/src/server.js:65` 返回全部邮件、附件记录和任务；`MailStore.swift:92` 整体替换状态 | 历史同步扩容时必须同时调整列表分页和正文加载，否则数据量会上涨到每次刷新中 |
| 搜索尚无全文索引 | `Backend/src/database.js:61` 遍历 JSON；`MailStore.swift:46` 在当前账号的内存记录中筛选 | 随邮件增多，查询和界面刷新成本增加；缺少结构化条件和跨账号搜索 |
| “回复全部”可能漏人 | `MailStore.swift:189` 将发件人设为 To，追加原 Cc，但未合并原 To 中的其他收件人 | 多人往来可能漏回参与者。当前已存在回复全部入口，应修正语义 |
| 会话数据不完整 | 收信记录有 Message-ID，但未保存用于会话归并的完整 In-Reply-To、References、Reply-To；Swift 邮件模型也无会话字段 | 难以可靠展示整段往来、选择正确回复地址，以及让 AI 理解此前约定 |
| AI 仍以单封上下文为主 | `Backend/src/agent.js:25` 组织当前邮件和附件作为总结、回复输入 | 容易缺少前几轮约定、已完成事项和对方最新要求 |
| 系统与数据保障仍待补齐 | README 明确记录通知、登录启动、正式签名等未接入或未完成；草稿仅本机保存 | 长期运行、升级恢复和跨设备继续写信仍有体验缺口 |

本节保留调研时的源码检查，文件行号对应 v0.0.5。历史回填、分页、回复收件人及引用头已在后续阶段修正；本机全文索引、会话阅读及联系人补全已在本轮实现；会话 AI 仍是后续候选，当前状态以下方确认清单及验收记录为准。

### 第一阶段：先解决每天收发的可靠性

**A. 先修复回复收件人，范围小、收益直接。**

- 保存并正确处理 Reply-To；回复全部合并发件人或 Reply-To、原 To、原 Cc。
- 按邮箱地址去重，排除当前账号及已确认的自身别名，避免依赖逗号直接拆分显示名。
- 保留实际收发账号归属；转发与回复使用各自的邮件头语义。
- 验收样例：A 发给“我、B”，抄送 C；我回复全部时，A、B、C 都应出现在合理的 To/Cc 中；自己不应重复出现。另测显示名含逗号、重复地址和 Reply-To 不同于 From。

**B. 把最近窗口同步扩展为可恢复的同步任务。复杂度高。**

- 每个账号、文件夹保存进度；继续使用已有 UIDVALIDITY 检查，并补充高水位 UID、历史回填边界及必要的状态检查信息。不要把现有代码已处理的 UIDVALIDITY 当作新增能力。
- 首次先显示最近邮件，再分批补齐旧邮件头；正文和大附件按需获取。首版可以先做可恢复轮询，再补收件箱 IDLE。
- 新邮件检查、旧邮件回填和本机待提交更改分别管理，采用有上限的重试及退避；一个账号失败不阻塞其他账号。
- 唤醒、网络恢复和服务重启后重新建立连接。IDLE 只能在进程运行且网络可用时提供近实时更新；退出或睡眠不能承诺持续收信。
- 对超限、损坏或暂时无法解析的邮件显示可重试记录，避免用户只能看到“同步成功”却不知道有邮件被跳过。
- UI 显示“正在接收新邮件 / 已加载历史范围 / 待提交更改 / 需要重新认证”，便于判断邮箱是否完整。

**C. 历史扩容必须配套分页与迁移。复杂度中高。**

- 保留轻量设置与状态接口，新增分页邮件列表；正文、附件文本和详细 AI 结果按需读取。会话索引可以在下一阶段增加。
- 为常用账号、文件夹、日期、UID 查询补索引；可以在现有 JSON 存储上增加查询字段或投影表，逐步迁移。
- 迁移按版本执行并记录成功状态。当前构造数据库时直接设 `user_version=1`，后续新增版本不能仍然无条件覆盖版本号。
- 迁移应保留本机草稿、AI 结果、分类、附件关联和待提交更改；提供可回退的备份方案。

第一阶段必须通过的验证：

1. 一个文件夹至少 1,000 封，跨越第 200 封后仍能继续加载；重复执行无重复项。更大数据量用于后续性能测量，不把 1,000 封当作产品上限。
2. 回填中途断网、关闭服务、重启，能够继续；网页端删除或移动的已缓存邮件能在校准后反映，不能只检查新 UID。
3. UIDVALIDITY 改变时，旧的待提交操作不会误作用于新邮件；本机 AI 结果等附加数据采用明确的恢复策略。
4. 一个账号认证失败时，其他账号仍可同步；失败任务有原因和重试入口。
5. 已读、星标、移动在离线修改后可提交，并且较新的本机操作不会被旧快照覆盖。
6. SMTP 成功、明确失败、结果不确定三种路径保持现有防重行为；测试不向真实外部邮箱发送邮件。

### 第二阶段：完整会话与高频写信

同一账号中以 Message-ID、In-Reply-To、References 建立会话；主题规范化只能作有限回退，不能只因主题相同就合并，也不能跨账号合并。保留每封邮件身份与所在文件夹，避免移动后丢失 AI 结果。

正文按时间展示、引用折叠；保存完整引用链。联系人先从本机历史收发记录产生建议，不必为此先接入云通讯录。当前优先范围为 A1、A2。格式编辑 A3 和服务器草稿同步 A4 保留为后续候选，分别覆盖基础格式及原文引用、纯文本备选，以及本机与远端同时修改的冲突。

会话 AI 输出“当前进展、尚未解决的问题、下一步行动”，并能跳转到依据邮件；有新回信时标记旧总结需刷新。回复继续使用现有预览和使用内容流程，用户编辑期间的模型结果不能覆盖已修改正文。

### 第三阶段：快速找到邮件

当前确认范围为 B1、B2；统一收件箱 B3、保存搜索 B4 与快捷键 B5 保留为后续候选。

先做可靠的关键词索引和条件筛选：`from:`、`to:`、`has:attachment`、`is:unread`、日期范围、账号、文件夹；同时索引附件名称、已提取文本和 AI 理解结果。全文索引不能替代历史同步，未缓存范围要明确展示，并提供继续同步或服务端搜索入口。

中文需要单独验证。不能直接假定默认 FTS5 分词能覆盖中文子串检索：至少测试“合同”“发票”等两字词、长句中间的词、中文文件名和中英混排；根据结果选择分词、n-gram 索引或受限回退。搜索查询解析、结果片段和排序同样需要验收。

统一收件箱只合并视图，账号归属始终明确。打开搜索结果、归档或回复时保持选中身份，避免列表刷新后跳到别人的邮件。常用快捷键优先覆盖搜索、下一封、回复、归档、撤销。

### 第四阶段：回复跟进与系统能力

回复跟进、提醒、稍后处理、通知和发送扩展均为后续候选。E1 完整备份恢复已提前纳入优先范围。

借鉴 Inbox Zero 的状态，将人工确认的“待我回复 / 等待对方 / 已完成”独立于未读和业务分类；AI 给状态建议，用户可修改。发出后可设置“若三天无回复再提醒”，对方新来信取消提醒，自己的补充邮件不能误判为对方回复。

稍后处理与提醒保存在本机，重新打开 App 时补处理到期事项。新邮件通知、通知跳转和未读角标先做正确；需要关闭 App 后仍执行的任务，应另行设计系统通知调度或后台服务，并明确睡眠时的限制。

撤销发送应先采用短暂延迟队列，例如 10 秒；SMTP 提交成功后不能承诺撤回。定时发送也必须显示本机执行条件，电脑休眠或 App 退出时不能标成已执行。

数据目录选择及迁移已在 0.0.10 完成，E1 完整备份恢复已在本轮完成，入口和容量边界见 [优先功能说明](PRIORITY_WORKFLOWS.md)。固定签名、正式分发和缓存加密分别保留为 E5、E6、E7 候选。正式分发需完成签名、公证与可靠更新；增加加密时需同时设计迁移、密钥恢复及附件策略。

## 4. AI 功能如何继续完善

以下三种持续工作流保留为后续候选，A1、A2、B1、B2、E1 已在本轮完成。会话 AI A5 在 A1 之后，自动处理 D2 在规则预览 D1 之后：

1. **处理清单**：把“需要我回复”与“等对方回复”展示为今日可操作清单，允许一键打开会话、起草或延后。
2. **保存整理规则**：例如“账单标记为财务”“含合同附件的来信标记为待审阅”，先提供匹配预览和处理记录，再逐步允许可撤销的自动分类。
3. **会话与附件联合理解**：显示“附件变了什么、这次需要我做什么”，引用具体来信或附件段落；不根据缺失的历史编造结论。

复用现有任务持久化、暂停恢复、确认应用和撤销机制。按消息版本、规则版本和模型配置去重；记录调用次数、耗时和服务商返回的实际用量，缺少用量时标明未知。重复查看优先复用已有结果，正文或附件变化后再提示更新。

规则自动化需要有明确的授权范围。现阶段已有发送确认机制；分类、拟稿可以逐步自动化，外发、删除和第三方上传应分别设计确认行为。邮件内容始终作为数据，不能改变任务权限或触发邮件里要求的任意外部操作。

## 5. 接入与代码参考的取舍

若主力邮箱继续是已验证的 QQ，或现有通用 IMAP/SMTP 可用的邮箱，优先完成上面的收发链路。当前计划暂时排除 Gmail / Outlook 专用接入与 OAuth，继续完善通用 IMAP/SMTP。

保持 SwiftUI + 本机 Node.js + SQLite 的总体结构。先拆清同步、查询、任务和发信的职责；服务商专用接口暂不安排。

代码采用前查看对应文件和版本的许可证：[Mailspring 的 README](https://github.com/Foundry376/Mailspring/blob/master/README.md) 标为 GPLv3；[Inbox Zero 的 LICENSE](https://github.com/elie222/inbox-zero/blob/main/LICENSE) 含 AGPLv3 及额外条款；Zero、MishMail、Postie 的仓库元数据标为 MIT。本次提供的是产品与实现思路参考，没有引入第三方代码。
